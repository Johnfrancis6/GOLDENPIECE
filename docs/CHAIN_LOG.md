## How to work on dev from a build session (read this first)

- The session network blocks the Postgres port (5432/6543): `supabase db
  push` hangs from a session. Use **`scripts/sb_api.py`** (Management API
  over HTTPS; the proxy injects the token):
  - `python3 scripts/sb_api.py migrate` — applies new `supabase/migrations/*`
    and records them in `supabase_migrations.schema_migrations` like the CLI;
  - `python3 scripts/sb_api.py test` — runs every `supabase/tests/*.sql`
    pgTAP file on dev inside a transaction that is always rolled back;
  - `python3 scripts/sb_api.py query "<sql>"`.
- CI (`deploy-dev.yml`) runs on every push to `main` **and `build/**`**:
  `supabase db push` (with the GitHub secrets), PostgREST + auth settings,
  `functions deploy`, smoke test of `health`. It reports "Remote database
  is up to date" when the session already applied the migrations — that is
  expected and proves history consistency.
- Supabase CLI 3.3.0 and Deno 2.9.6 install with `npm i supabase deno` (in
  a scratch dir). `supabase functions deploy <fn> --remote=<ref> --use-api --yes`
  works from a session.
- Migrations are immutable once applied: fix with a **new** migration.
- PUBLIC keeps EXECUTE on new functions (per-schema default privileges
  cannot remove it): end every migration that adds functions with
  `revoke execute on all functions in schema api, core, ref, mkt, analytics, ops, sim from public;`
  then grant explicitly. `supabase/tests/schema_guard.test.sql` fails otherwise.
- pgTAP files: start with `grant usage on schema extensions to anon,
  authenticated, batch_writer;` when you switch roles (pgTAP lives in `extensions`).
